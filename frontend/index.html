01 · The role

What an automation engineer actually does

Not a job title you apply for so much as a capability you sell. You find work that humans repeat, replace it with a system that runs itself, keep it alive, and prove it saved money. Five moves:

01Map the work. Sit with a process, find the repetitive rule-based steps that eat hours, and decide what is worth automating.
02Wire the systems together. Connect apps and APIs so data flows without a human copy-pasting: forms, CRMs, databases, spreadsheets, email, Slack.
03Add judgment with AI. Where a step needs reading, deciding, or drafting, call an LLM or an agent instead of a person. The premium tier today.
04Make it reliable. Handle errors, retries, and edge cases. Monitor it. Get alerted when it breaks. This separates a $500 toy from a $2K per month system.
05Prove the value. Document it, hand it off, and quantify hours and cost saved. That number gets you paid and renewed.

06 · Go deeper: AI agents

From workflows to agents, the frontier of stage 4

An agent is just an LLM in a loop: it thinks, calls a tool, looks at the result, and repeats until the job is done.

This is where the money and the moat are, and it is the exact skill the data points to. Below is the mental model, a deeper hands-on path with its own progress, and every resource worth your time. Anthropic's core rule sits over all of it: start simple, and add complexity only when it earns its place.

The mental model

Tap any idea to expand it. These seven concepts are the whole game.

The augmented LLM, the building block

The unit an agent is built from is a normal LLM given three extra powers: it can call tools, retrieve information, and keep memory. Everything else is orchestration around that. Get one augmented LLM call reliable before you build anything bigger.

The agent loop: Thought, Action, Observation

An agent runs a cycle: Thought (decide the next step), Action (call a tool), Observation (read the result), then loops with that new information until it decides it is finished. This is the single idea the whole field is built on. The Hugging Face course drills it directly.

Workflows vs agents, and why it matters for your bill

Anthropic draws a sharp line. A workflow follows a fixed path you coded. An agent lets the model decide the steps at runtime. Workflows are cheaper, faster, and more predictable, so use them whenever the steps are known. Reach for a true agent only when the steps genuinely cannot be predicted. Most "agents" clients need are actually workflows.

The five patterns that cover almost everything

Anthropic's guide names five reusable patterns: Prompt chaining (steps in sequence), Routing (send each input to a specialist), Parallelization (run independent subtasks at once), Orchestrator-workers (a lead model splits a task and delegates), and Evaluator-optimizer (one model drafts, another critiques and improves). Learn these five and you can design most systems.

Tools and MCP, how an agent acts on the world

Tools are functions the model can call: search, send an email, query a database. MCP (Model Context Protocol) is the open standard, from Anthropic, for exposing tools, data, and prompts to any model in a consistent way. Learn MCP and your tools work across Claude, n8n, and other clients instead of being wired one at a time.

RAG and memory, giving the model real, current data

RAG (retrieval-augmented generation) puts your documents into a vector database, retrieves the relevant pieces at question time, and feeds them to the model, so it answers from your data instead of guessing. Memory is state that survives across steps of the loop. Together they turn a clever demo into something that knows a specific business.

Evals and guardrails, the line between demo and production

An eval is an automated test that scores an agent's output so you know if a change made it better or worse. Guardrails stop it from doing something unsafe or off-task. This is the unglamorous half almost no one does well, which is exactly why clients pay a premium for someone who does.

Databases

You already know the mechanics. This is the judgment layer: the eight decisions that keep a database from losing trust, money, or a client at the worst moment.

The eight laws Short version Roadmap Resources
01 · The eight laws

What actually matters about databases

Your apps are ledgers: a fiado balance, a client's revenue, a payment record. The database is the product's promise. Get it right and "your data is safe and correct" becomes a real selling point for high-ticket work.

1

Choose the boring database

Default to Postgres. Reach for anything else only when a real constraint forces you.

It does relational, JSON, full text, geospatial, and vector in one engine you already know, and Supabase gives it to you managed. Snowflake and BigQuery are for analytics, never the live app. Redis is a layer, not a home. A second database type triples your failure modes, so earn that cost.

2

Model for how you read

Normalize until it hurts, then denormalize until it works.

Start normalized so writes stay correct, then denormalize only a proven hot path. Use stable surrogate keys, and put real foreign keys and constraints in the schema. And never store money as float: use numeric or integer cents, or rounding will bite a fiado balance.

3

Indexes are the line between fast and dead

Index what you filter, join, and sort by. Nothing else.

A missing index is why an app that felt instant at 100 rows crawls at 100,000. But every index slows writes, so do not index everything. Read the plan instead of guessing.

EXPLAIN ANALYZE SELECT * FROM ledger_entries
WHERE vendor_id = 42 AND created_at > now() - interval '30 days';
-- Seq Scan under a filter = your signal to add an index.
4

Transactions are how you keep promises

If two facts must both be true or both false, they belong in one transaction.

Recording a payment and lowering a balance are one atomic act, never two hopeful writes. Then know your isolation level: the default lets two requests read a balance and clobber each other. Under real concurrency, raise isolation or take SELECT ... FOR UPDATE. Keep transactions short, and never hold one open across an external API call.

5

Migrate without downtime

Every schema change is a migration in version control, run by a tool.

On a live table, expand then contract: add the new column, backfill in batches, ship code that writes both and reads the new, then drop the old later. Never rename or drop in the deploy that stops using it. A dropped column is gone except from backup.

6

Assume the client is hostile

The database enforces who sees what. The frontend is a suggestion.

On Supabase this is the lesson: the moment a database is reachable from a browser, Row-Level Security is the wall. Add least privilege, keep secrets out of the bundle, parameterize every query, and use TLS.

ALTER TABLE ledger_entries ENABLE ROW LEVEL SECURITY;
CREATE POLICY "owner reads own rows" ON ledger_entries
  FOR SELECT USING (vendor_id = auth.uid());
7

Scale in the right order

Most scaling problems are a missing index wearing a costume.

Walk the ladder and stop when the pain stops: fix the index and query, add connection pooling, then a cache, then read replicas, and only at real scale, partition or shard. On scan-priced warehouses, partition and select columns explicitly, because SELECT * over a wide table is a literal invoice.

8

A backup you have never restored is a rumor

You do not have backups until you have restored one and watched it work.

Turn on point-in-time recovery, then actually restore into a scratch environment. Monitor slow queries, connections, replication lag, and disk, and alert before disk fills, because a Postgres that cannot write is an outage.

What it is Roadmap Resources
01 · First, what is it

Cloud computing vs cloud engineering

Cloud computing is renting computers, storage, and databases over the internet instead of owning them. Cloud engineering is the job of designing and running systems on it.

You already self-host on a VPS with Docker, so this is not a new world, it is the next step up: the same instincts at client scale, with managed services that do the hard parts and certificates that raise your rate. Should you learn it? Yes, the fundamentals. You do not need to become a full-time cloud engineer. You need enough to deploy, scale, and secure what you build, and one cert to prove it.

Why it paysAWS-certified engineers earn noticeably more than uncertified peers, and there are tens of thousands of open cloud roles at any time. For you it is leverage: host client systems reliably instead of on a single fragile server.

Tech, explained from zero

Never touched code? Start here. No jargon. By the end you'll understand what everyone in tech is actually talking about: software, hardware, the web, and the tools.

The machine Programming The web Your tools
01 · The machine

What a computer actually is

A computer is just a machine that follows instructions very fast. It has two halves: the physical parts (hardware) and the instructions (software).

Hardware, the physical parts

Hardware is anything you can touch. The CPU is the brain that does the calculations. RAM is short-term memory: fast, but wiped when you turn the machine off. Storage (SSD or hard drive) is long-term memory that keeps your files. The screen, keyboard, and mouse are hardware too.

Think of a kitchen: the CPU is the cook, RAM is the counter space you're working on right now, and storage is the pantry.

Software, the instructions

Software is the set of instructions that tells the hardware what to do. You can't touch it. An operating system (Windows, macOS, Android) is the software that runs everything else. Apps (a browser, WhatsApp, a game) are software built to do one job.

Hardware is the body; software is the thoughts telling it what to do.

02 · Programming

What programming really is

Programming is writing the exact, step-by-step instructions a computer follows. The computer is fast but literal: it does exactly what you say, nothing more.

The logic (the whole game)

Almost all code is built from four simple ideas. Variables are labeled boxes that hold a value (a name, a number). Sequence is doing steps in order, top to bottom. Conditions (if / else) make decisions: "if the user is logged in, show the dashboard, else show login." Loops repeat a step many times so you don't write it a thousand times.

That's it. Every app, no matter how big, is those four ideas stacked up.

What a programming language is

A programming language lets you write instructions in something closer to human words, which the computer then translates into its own 1s and 0s. Python reads almost like English and is great to start with. JavaScript runs in every web browser. There are many, but the logic above is the same in all of them, so learning one makes the next far easier.

Why logic matters more than the language

Beginners think they need to memorize a language. You don't. You need to think in steps and conditions. Once you can break a problem into "first do this, then if that, repeat this," writing it in any language is just looking up the exact words. Learn the thinking, not the syntax.

03 · The web

The internet, the web, and the words people mix up

The internet is the roads. The web is one kind of traffic on those roads. And "website" vs "web app" trips everyone up, here's the difference.

Internet vs the web

The internet is the global network of cables and computers connected together, the roads. The web is the system of pages and links you browse on top of it. Email and video calls also use the internet but are not "the web." So the web is one thing that runs on the internet, not the same as it.

Web page vs website vs web app

A web page is a single page. A website is a collection of pages about one thing, usually to read (a blog, a restaurant's site, a news site). A web app is a website you use and interact with, like a tool: Gmail, Google Docs, Netflix, or this academy. The line is simple: a website you mostly read; a web app you do things in.

Frontend vs backend

The frontend is everything you see and click in the browser: buttons, colors, layout. The backend is the engine on a server you never see: it stores data, checks your password, and does the heavy work. When you log in, the frontend takes your password and the backend checks it. Most apps need both.

What a server is

A server is just another computer, always on, that other computers ask for things. When you open a website, your browser (the client) asks a server for the page, and the server sends it back. "The cloud" is mostly just someone else's servers you rent instead of owning.

04 · Your tools

The tools you'll actually use

You don't need much to start. Here are the words for the tools every developer uses daily.

Files, folders, and extensions

Code lives in files, organized in folders. A file's extension (the bit after the dot) says what kind it is: .html for a web page, .css for styling, .js for JavaScript, .py for Python. The computer uses it to know how to read the file.

A code editor / IDE

You write code in a code editor. The most popular is VS Code, and it's free. An IDE (Integrated Development Environment) is a code editor with extra tools built in: running code, debugging, autocomplete. For most beginners VS Code is all you need, and people use "editor" and "IDE" loosely.

The terminal (command line)

The terminal is a text window where you type commands instead of clicking. It looks intimidating but you only need a handful of commands. It's how you run programs, install tools, and use Git. Every developer lives in it a little.

Git and version control

Git saves snapshots of your code as you work, like save points in a game, so you can go back if you break something. GitHub is a website that stores those snapshots online and lets people work together. You'll learn it early; past your first project it's non-negotiable.
