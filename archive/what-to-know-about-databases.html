What actually matters about databases

You already know the mechanics: ETL, star schemas, Postgres, Snowflake, BigQuery, dbt. So this is not a tutorial. It is the judgment layer: the eight decisions that separate a database that quietly holds a business together from one that loses trust, money, or a client at the worst possible moment.

Why this is worth your time

Your apps are ledgers. A fiado balance, a client's revenue data, a payment record. The database is the product's promise. Get it right and "your data is safe and correct" becomes a real selling point for high-ticket work. Get it wrong once and the trust never comes back.

01
Choose

Pick the boring database on purpose

Default to Postgres. Reach for anything else only when a real constraint forces you.

Most "we need a special database" instincts are premature. Postgres does relational, JSON, full text search, geospatial, and now vector search in one engine you already know. It carries a product from first user to millions. The exotic options solve problems you probably do not have yet, and each one adds an operational tax you pay forever.

PostgresThe default. Transactional apps, mixed workloads, anything with money or relationships. Supabase gives you it managed.
SQLiteUnderrated. Local-first, edge, single-tenant tools. Your PWA prototypes can start here before a server exists.
Snowflake / BigQueryAnalytics, not the app. Scan-heavy reporting over history. Never the live transactional store.
RedisA layer, not a home. Cache, queues, rate limits, sessions. Not your source of truth.
Mongo / documentOnly for genuinely schemaless data. Most "flexible" schemas are relational schemas you have not modeled yet.
GotchaSplitting into a second database type triples your failure modes: two backup stories, two consistency models, two things to monitor. Earn that cost, do not assume it.
02
Model

Model for how you read, not just how you store

Normalize until it hurts, then denormalize until it works.

Your data-warehouse instinct is dimensional. For an application store, invert the priority. Start normalized so writes stay correct and there is one source of truth for every fact. Then, only where a hot read path proves it needs it, denormalize deliberately: a cached balance, a counter, a materialized view. The mistake is denormalizing early for a read that never becomes hot.

Choose keys with intent. Prefer a stable surrogate key (a bigint identity or a UUID) over anything a human might want to change later. Put real foreign keys and constraints in the schema. The database enforcing your rules is worth more than every application-layer check, because the database is the one thing every path goes through.

For a money appNever store money as float. Use numeric / decimal, or integer cents. Floating point rounding on a fiado balance is a bug you will not see until a vendor does.
03
Index

Indexes are the line between fast and dead

Index what you filter, join, and sort by. Nothing else.

A missing index is the single most common reason an app that felt instant at 100 rows crawls at 100,000. But an index is not free: every one slows writes and costs storage, so indexing every column is its own bug. The skill is reading the plan, not guessing.

-- Stop guessing. Ask the planner what it actually does.
EXPLAIN ANALYZE SELECT * FROM ledger_entries
WHERE vendor_id = 42 AND created_at > now() - interval '30 days';

-- Seq Scan on a big table under a filter = your signal to index.
CREATE INDEX idx_ledger_vendor_recent
  ON ledger_entries (vendor_id, created_at DESC);

Learn to spot Seq Scan where you expected a lookup, watch the row estimates diverge from reality, and put the most selective column first in a composite index. This one habit, reading EXPLAIN ANALYZE, resolves the majority of "the app is slow" tickets you will ever get.

04
Transactions

Transactions are how you keep promises

If two facts must both be true or both be false, they belong in one transaction.

ACID is not academic once real money moves. Recording a payment and lowering a balance are one atomic act, never two hopeful writes. Wrap them so a crash between them can never leave the ledger half updated.

BEGIN;
  UPDATE accounts SET balance = balance - 50 WHERE id = 1;
  INSERT INTO payments (account_id, amount) VALUES (1, 50);
COMMIT;  -- both land, or neither does

Then know your isolation level. The default (READ COMMITTED) allows two concurrent requests to both read a balance, both act on it, and clobber each other. For anything where correctness under concurrency matters, either raise isolation or take an explicit row lock with SELECT ... FOR UPDATE. This is the class of bug that only appears under load, in production, with real users, which is the worst time to learn it exists.

Rule of thumbKeep transactions short. A transaction held open while you call an external API locks rows and starves everyone else. Do the slow work outside the lock.
05
Migrate

Schema changes without downtime

Every schema change is a migration in version control, run by a tool, never by hand.

The schema will change forever. Treat migrations like code: small, reviewed, reversible, and applied the same way in every environment. Ad hoc ALTER TABLE on production by hand is how a Friday becomes a weekend.

On a live table, the pattern that avoids downtime is expand then contract. Add the new column or table, backfill it in batches, ship code that writes to both and reads the new, then remove the old once nothing depends on it. Never rename or drop in the same deploy that stops using it. A dropped column is unrecoverable except from backup, so the slow, boring, multi-step path is the professional one.

WatchOn big Postgres tables, an unguarded ALTER can take a lock that blocks all reads and writes. Know which operations lock before you run them at 2pm.
06
Secure

Assume the client is hostile

The database enforces who sees what. The frontend is a suggestion.

Since you build on Supabase, this is the most direct lesson: the moment a database is reachable from a browser, Row-Level Security is not optional, it is the wall. Without it, anyone who reads your JavaScript can query every row. With it, the rule that a user only ever touches their own data lives in the database, where no client can route around it.

ALTER TABLE ledger_entries ENABLE ROW LEVEL SECURITY;

CREATE POLICY "owner reads own rows"
  ON ledger_entries FOR SELECT
  USING (vendor_id = auth.uid());

The rest is old discipline you already have: least privilege on every database role, secrets and connection strings never in the frontend bundle, always parameterized queries so user input can never become SQL, and TLS on the wire. Encrypt the genuinely sensitive columns at rest. None of this is exotic. All of it is the difference between a breach and a non-event.

07
Scale

Scale in the right order, and not before you must

Most scaling problems are a missing index wearing a costume.

Founders reach for sharding and microservices when the real fix was one index and a rewritten query. Walk the ladder in order, and stop as soon as the pain stops:

1 · Index + queryRead the plan, fix the N+1, add the index. Solves the overwhelming majority of slowness.
2 · Connection poolingPostgres hates thousands of raw connections. Put a pooler (PgBouncer, Supabase's) in front.
3 · CacheRedis or a materialized view for expensive, rarely-changing reads. Now you inherit invalidation, so cache on purpose.
4 · Read replicasSend heavy reads to replicas. Accept replication lag: a replica can be a moment behind.
5 · Partition / shardLast, and only at real scale. It buys throughput and costs you a great deal of simplicity.
Cost, your BigQuery worldOn scan-priced warehouses you pay per byte read. Partition and cluster on the columns you filter by, and select columns explicitly. SELECT * over a wide table is a literal invoice.
08
Survive

A backup you have never restored is a rumor

You do not have backups until you have restored one and watched it work.

This is the unglamorous section that saves the business. Turn on automated backups and point-in-time recovery, then actually run a restore into a scratch environment and confirm the data comes back whole. The day you need it is not the day to discover the backups were empty.

Around that, build the senses to know something is wrong before a client tells you: monitor slow queries, connection counts, replication lag, and disk. Set an alert before disk hits full, because a Postgres that runs out of disk stops accepting writes, and a store that cannot write is an outage. Boring, automated, and tested beats clever every time here.

The trust angle"We take nightly backups, we have tested restores, and your data is isolated per tenant" is a sentence that closes cautious high-ticket clients. Most of your competition cannot say it truthfully.

If you remember nothing else

Default to Postgres. Add another engine only when a real constraint forces it.

02

Let the database enforce your rules. Constraints, foreign keys, and RLS beat every app-layer check.

03

Read EXPLAIN ANALYZE before you optimize. Most slowness is one missing index.
